# Running Without a JavaScript WASI Shim

Link `WASIShim` to implement WASI in Swift, so the app needs no JavaScript WASI implementation.

## Overview

The Swift standard library and wasi-libc talk to the host through `wasi_snapshot_preview1` imports. By default, the package generated by `swift package js` provides them with a JavaScript WASI shim ([`@bjorn3/browser_wasi_shim`](https://github.com/bjorn3/browser_wasi_shim) or [`uwasi`](https://github.com/swiftwasm/uwasi)).

`WASIShim` implements them in Swift instead, on top of JavaScriptKit, so the linked app has no WASI imports left. The package generated by `swift package js` then leaves out the JavaScript WASI shim and its npm dependency.

## Opting in

The shim is meant for apps that run in a browser or in Node.js. Add the product to your executable target:

```swift
.executableTarget(
    name: "App",
    dependencies: [
        .product(name: "JavaScriptKit", package: "JavaScriptKit"),
        .product(name: "WASIShim", package: "JavaScriptKit"),
    ]
)
```

There is nothing to import or call. Apps that don't depend on the product are unaffected. On other platforms, such as a host build for Xcode, the module is empty.

Don't add a `condition:` to this dependency: `swift package js` then won't see it and will leave out the glue code the shim needs.

Keep it out of library targets that your tests depend on. Tests that `swift package js test` runs need a file system and arguments, which `WASIShim` doesn't provide, so they should keep using `uwasi` or `@bjorn3/browser_wasi_shim`.

The shim works with Embedded Swift and with the full standard library. It requires Swift 6.4 or later and a single-threaded `wasm32-unknown-wasip1` target: building it with an older compiler or for `wasm32-unknown-wasip1-threads` fails with an error.

## Behavior

- Standard output goes to `console.log` and standard error to `console.error`, one call per line. Invalid UTF-8 becomes U+FFFD.
- Random bytes come from `crypto.getRandomValues`, and clocks from `Date.now()` (realtime) and `performance.now()` (everything else).
- `sleep`, `usleep`, `nanosleep` and `Thread.sleep` block for the requested time. They wait with `Atomics.wait` where the host allows it (workers, Node.js) and otherwise busy-wait, so a sleep on the browser main thread freezes the page for its duration.
- `exit` writes any pending partial line and ends the program, as with a JavaScript WASI shim: the package generated by `swift package js` calls `process.exit` in Node.js, and elsewhere JavaScriptKit's runtime throws a `ProcessExit` error that carries the exit code.

## Known limits

- There is no file system: opening a file fails with `ENOENT`, and other file operations fail with `EBADF` or `ENOTSUP`.
- Reading stdin returns end of file.
- `poll` and `select` with a timeout or several file descriptors fail with `ENOTSUP`.
- Arguments and environment are empty. CPU-time clocks report the monotonic clock.
- A trailing partial line is written by `exit` only. When `main` returns without calling `exit`, output without a final newline is not shown.
